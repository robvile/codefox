# Changelog

## 0.7.0 — 2026-11-24

- **ComfyUI finds itself — "Scan for ComfyUI".** The ComfyUI panel has a new **Scan for ComfyUI** button: CodeFox checks the standard Windows locations in order (ComfyUI Desktop user data in %APPDATA%, Documents, the home folder, portable C:\ / D:\ installs, and the program folder) plus the server URL, and reports exactly what it found at each place — workflows folder and how many workflow files, model counts per category (checkpoints, LoRAs, VAE, CLIP, UNet, ControlNet, embeddings, upscale models), and whether custom_nodes is present. When a workflows folder is found it is adopted automatically and its workflows imported (recursively, so subfolders count). The scan is bounded — only the listed roots, no whole-drive walk — and the manual Browse picker stays as the fallback. Nothing is invented: a location that is not there is reported as not found.
- **The capabilities panel now shows everything.** When ComfyUI answers but no familiar node family is found, the panel no longer stops at that one line: it lists every node class `/object_info` reported (count plus a scrollable list), so you can see exactly what an install has. If `/object_info` comes back empty it says so plainly. Image generation is now also recognised from Flux / SD3-style graphs (a sampler + UNet loader + CLIP loader + VAE loader), which never use CheckpointLoaderSimple — the old check missed those installs entirely. Matching is case-insensitive. A capability is still only listed when the nodes really exist.
- **Simple generation — Midjourney-easy, no iframe.** Each workflow now has a simple Generate form above the advanced inputs: a big Prompt box and a Negative prompt box (labelled from the workflow's own wiring — which CLIPTextEncode feeds the sampler's positive/negative input, including BasicGuider wiring in Flux-style graphs; when the wiring cannot tell them apart the boxes are labelled Prompt 1 / Prompt 2 and say so), Seed with a Random button, Steps, CFG and Denoise — only for KSampler nodes and only the inputs that node actually exposes — and size presets (Square 1024, Portrait 832×1216, Landscape 1216×832, plus custom W/H) only when the workflow has a latent-size node. One Run button; progress, thumbnails, History and Import work exactly as before, and the existing advanced panel (every input) and the Agent ```comfyui block are unchanged. A workflow with no text-prompt input says so plainly and shows no fake prompt boxes. ComfyUI's web UI is never embedded.
- **Version.** package.json is now 0.7.0; the sidebar footer reads "CodeFox 0.7.0 — Local · No account needed".

## 0.6.4 — 2026-11-24

- **FIXED: the dead-buttons bug — root cause found and proven in real Electron.** The window's bridge to the main process (`window.rb`) was never created, so every button that needs the main process silently did nothing: the project dropdown, creating a conversation, LM Studio verify / refresh models, and the Developer tools button. The cause: `preload.js` loaded two helper files with `require('./unity-assets')` and `require('./mcp-presets')`. In real Electron that throws ("module not found: ./unity-assets") — the preload dies before it reaches `exposeInMainWorld`, so the bridge never exists. Plain Node never showed it, because `require` works fine there, which is why the code audit and the Node harness both passed while the installed app stayed broken. It broke in v0.5.1, the release that added the first local-file require to the preload. The fix: the preload no longer requires any local file — only `electron`. The two static data tables it needs (the Unity asset extensions and the MCP preset list) now come from the main process over a synchronous channel (`app:staticData`), and the small pure helpers (`isUnityAssetPath`, `getPreset`, `buildServerEntry`) live in the preload itself, implemented from that data. The `window.rb` shape the app sees is unchanged, so no app behaviour changed — the same buttons now work because the bridge exists.
- **Verified in real Electron, not just in Node.** The real `preload.js` was run in a real Electron 36 window under Xvfb: `typeof window.rb` is now `"object"` (it was `"undefined"` before the fix), all 13 sections are present, the preset list has all 10 presets, `buildServerEntry` accepts a valid token and refuses a missing one, and `rb.app.ping()` resolves. The real `index.html` + `app.js` were also loaded with stubbed main-process handlers: the bridge banner stays hidden, the startup log reads "[bridge] ping ok", and init runs through to the Home view. (The packaged Windows installer and Rob's install are still the final confirmation.)
- **Regression guard.** The smoke test now enforces the invariant that would have caught v0.5.1: `preload.js` may not require any local file (only `electron` / Node built-ins), and it checks the preload's local copies of the helpers agree with the real modules on a matrix of inputs, so the two copies cannot drift silently.
- **Version.** package.json is now 0.6.4; the sidebar footer reads "CodeFox 0.6.4 — Local · No account needed".

## 0.6.1 — 2026-11-24

- **BUG FIX — `git pull` no longer blocks on files the build itself rewrites.** Twice, a pull was blocked by local modifications to files the normal build/install cycle creates: first `package.json` (the allowScripts entry from `npm install-scripts approve electron`) and `package-lock.json` (rewritten by `npm install`), then `package-lock.json` again and `unity-bridge-source.js` (regenerated by every build). The root cause: `unity-bridge-source.js` is a generated file that was tracked in git, so the working tree was dirty after every build and the next pull refused to overwrite it. Fixed the way the app icons were already fixed: the file is now generated and gitignored (regenerated by `scripts/embed-bridge.js` at install, start, and build time), and it is no longer tracked — the file still exists on disk locally, it just is not in git. `npm start` now has a `prestart` step and `npm install` a `postinstall` step that regenerate it (and the icons) so a fresh clone works without it. What changes for you: `git pull` should just work with no restore step; use `npm ci` instead of `npm install` when dependencies change, because `npm ci` installs exactly what the lockfile says and never rewrites it. The lockfile on GitHub is also being synced (it still said version 1.0.0 while local installs had moved on to Electron 36.9.5).

## 0.5.2 — 2026-11-24

- **BUG FIX — toggling the Unity bridge off did nothing.** The toggle removed the bridge file and showed a "Bridge removed" toast, but the toggle stayed ON — because the Connections view re-rendered right after the removal and its auto-install put the bridge straight back. Root cause: the auto-install only checked "is the file missing" and had no memory of the user turning it off. Fixed with a persisted per-project `bridge_enabled_<id>` flag: toggle off sets it to 0 and removes the file, and every auto-install / auto-update path (startup, connect, switch, folder change, opening Connections) respects it, so off stays off. Toggle on sets it back to 1 and installs. The toggle's state is always re-read from disk after each operation.
- **BUG FIX — the CS1501 bridge error survived the v0.5.1 fix.** The fix was in the repo, but v0.5.1's auto-install only installed when the bridge file was MISSING — and a project that already had the broken bridge (installed by v0.5.0) kept it, so Unity kept reporting `error CS1501: No overload for method 'CreateAnimatorControllerAtPath' takes 2 arguments`. Fixed with bridge versioning: the bridge file now carries a `// CodeFoxBridge version: 0.5.2` marker and a `BridgeVersion` const, and CodeFox compares the installed version against the bundled one. On startup, connect, switch, or opening Settings → Connections, an out-of-date bridge is now overwritten automatically (toast: "Bridge updated to v0.5.2"). Upgrading from v0.5.0 to v0.5.2 fixes TD Pizza Racer's bridge on the next launch with no clicks — Unity may need a reimport/restart to clear the stale error. The v0.5.1 1-argument fix was verified still present in both the `.cs` file and the embedded copy.
- **Update plugin button is now disabled until it is needed.** It is greyed out with the tooltip "Bridge is up to date" while the installed bridge is current, and becomes clickable only when the installed bridge is older than the bundled one (or missing). Clicking it overwrites the bridge with the bundled copy, and it disables itself again afterwards. Its state is computed from the installed-vs-bundled version, not a guess.
- **The model MUST output the file, not just describe the fix.** A local model told to fix the CS1501 error replied that it "cannot modify files" — a prompt failure, not a capability failure, since the apply pipeline already works end-to-end (it created TestTMP.prefab). The system prompt now orders the model, in Agent mode: it MUST edit the project's files when asked to fix, change, create, or edit code, and describing the fix, explaining it, or saying it cannot modify files is a FAILURE. The app also enforces it: a refusal ("cannot modify files" and similar) triggers one automatic correction turn, and a reply with no file actions at all when the user asked for a change is treated as an incomplete turn and triggers one automatic follow-up demanding the file. One retry each at most; if the model still does not output the change, the loop stops and says so. The file parser also accepts ```` ```file:path ```` blocks as well as the documented `**File Path:**` + fenced block format (and a bare path line before a code block). **Diagnose error** now runs in Agent mode and, when the message is sent, the file named in the error is read and its surrounding lines attached to the prompt with an instruction to output the fixed file. A local model can still fail to comply — this is prompt engineering plus enforcement, not a guarantee. A short hint under the composer in Agent mode says the mode writes code to the project, with a snapshot taken first and revert available.

Not compiled inside a real Unity Editor here — confirm the error is gone after reinstalling v0.5.1 and letting the bridge auto-install.

## 0.5.0 — 2026-11-24

- **Agent mode is now a real loop (Agent mode only).** After each reply, CodeFox parses the reply for actions — file changes, ```powershell / ```pwsh / ```shell blocks, ```upm-install / ```upm-remove blocks — runs the allowed ones, asks about the rest, appends every result as a tool-result message in the thread, and calls the model again with the extended history, so it can build, see the error, fix it, and rebuild without another prompt. Ask and Plan modes are unchanged: one reply, then the bars, no looping. New `runAgentTurn` / `streamOneTurn` flow in app.js; the old one-shot `onDone` handler is gone.
- **Max rounds + Stop.** New `agent_max_rounds` setting (default 5, range 1–10, in Settings → Advanced). The loop stops when a reply has no actions, when the max is hit ("Stopped after N tool rounds — the task may need more steps. Ask me to continue if you want."), or when the user clicks the new **Stop** button under the reply ("Stopped by user."). The max is a hard cap. A status line under the reply shows the current round and the last action ("Working… round 2/5 — ran `dotnet build`").
- **Approval pauses that resume.** When an action needs approval, the loop pauses on the existing bar (apply bar / shell bar / new package bar) instead of skipping or running it. Approving runs the action, appends its tool result, and resumes the loop; dismissing appends a "User declined" note and resumes, so the model can try a different approach. The system prompt (Agent mode only) now tells the model it can use ```powershell and ```upm-install blocks, that output comes back as tool results, and that it should stop and summarise when done.
- **Unity Package Manager (manifest-based).** New IPCs `unity:listPackages`, `unity:addPackage`, `unity:removePackage` in main.js (backed by the plain-Node helper `upm-manifest.js`, unit-tested in the smoke test). CodeFox edits `Packages/manifest.json` directly — it does not claim to use Unity's Package Manager API — backs it up first to `Packages/manifest.json.codefox-bak`, writes it back with 2-space indent, and triggers a Unity refresh via the existing sentinel. The project scan now includes installed packages (requested + locked versions) so the model knows what is already installed, and Settings → Connections (and the Connections view) lists them under the Unity row with a per-package Remove button (confirm click).
- **Package installs always ask.** There is no auto-run path for packages — not in Auto Mode, not with auto-accept on. The new package bar (`package-bar`) shows the name + version, with an editable version field when the model gave none (Install stays disabled until a valid version is typed — a version is never guessed) and an editable name field for a bare git URL. ```upm-remove blocks work the same way with a Remove button. The smoke test asserts the install call is only reachable from the approval-bar handler.
- **Safety, extended and visible.** Dangerous commands now also include `rmdir /s`, `rd /s`, and `Remove-Item -Force -Recurse` — they never auto-run in any mode. Settings → Advanced has a new "What runs automatically, what always asks" summary and the max-rounds setting. A loop never runs a command while the shell is off, and never installs a package while no project folder is set.
- **BUG FIX — Unity bridge install failed in the installed app.** Root cause, confirmed: `unity:installBridge` read the bridge from `unity-companion/CodeFoxBridge.cs` under the app folder, but electron-builder's `build.files` list never included `unity-companion/`, so the installed app had no such file and every install (Update plugin, enable toggle) failed with a "Companion script not found in the app install" warning. Fixed in three layers: (1) packaging — `unity-companion/**/*` (plus the new `upm-manifest.js`, `unity-bridge.js`, `unity-bridge-source.js`) is now in `build.files`, so the file is in the installed app; (2) embedded fallback — `scripts/embed-bridge.js` (run before every build) generates `unity-bridge-source.js` from the `.cs` file, and `unity-bridge.js` installs from the bundled file first and the embedded copy when it is missing, so the install can never fail for a missing source file — the old warning is gone entirely; (3) auto-install on connect — the bridge installs automatically when a project is created, switched to, or given a new folder, when the app starts with a project already set, and when Settings → Connections is opened on a project without one; a real failure (e.g. folder not writable) is shown as the status there. The audit found no other runtime file with the same packaging gap: the only other files the installed app reads from its own folder are `preload.js` and `build/icon.png`, both already in `build.files`.
