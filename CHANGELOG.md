# Changelog

## 0.15.0 — 2026-11-26

- **The play-test loop — run the game and watch what it does.** The assistant can now test its own work in Play Mode instead of asking you to run the game: `set_play_mode` enters Play Mode for a fixed time (`{"action": "set_play_mode", "enabled": true, "durationSeconds": 10}` — the timed form is the default, capped at 120 seconds, because a model that enters without a duration can forget to stop it; without a duration it enters and stays, for reading live state, and is stopped afterwards with `{"enabled": false}`), then exits and reports the console since the run started — error count, error occurrences, warning count, the first 5 error lines, and a cursor for `readConsole`. Entering usually reloads the domain, so the handler keeps its state in SessionState and a poll tick finalizes it, the same pending pattern as the compile report; `readConsole` still works while a timed run is in progress. Compile errors block Play Mode (fix them with `recompile_and_report_errors` first), and the compile action now refuses while the game is running — the loop stops the game before touching code, because edits in Play Mode trigger recompiles that disrupt the run. The loop without vision: edit → recompile → run 10 seconds → read the report → `readConsole` since the cursor for details → fix and repeat. The model only sees what the game logs, so it adds deliberate log lines (`[Test] Player reached checkpoint 2`) when it needs to observe something.
- **`read_component_values` — live state off a scene object.** Two modes, because SerializedObject only exposes serialized data and the runtime values worth testing (a Rigidbody's velocity, a Transform's world position, a private `currentHealth`) are not in it: serialized properties (Inspector-visible fields, live in Play Mode, no names needed up front) and runtime members (properties/fields named explicitly, read by reflection). A path on its own lists the components and children instead, so the model never has to guess the scene tree. Output is bounded — 40 properties by default (100 hard max), collection items 8, nesting depth 2, strings 200 chars, floats to 3 decimals — and truncation returns `omitted` plus the available names so the model can ask for specific ones. Values are converted to plain JSON first (a raw Vector3 can recurse through `normalized` and throw); `renderer.material` / `meshFilter.mesh` are refused with a pointer to the `shared*` versions, because reading them instantiates a copy and leaks it. Unknown runtime members come back with a "Similar:" list. Read-only — writing is a separate action with approval and undo (next build). A timed run destroys the scene objects when it exits, so values can only be read while Play Mode is still running: enter without a duration, wait, read, stop. The honest limit is stated in the prompt: the model can read state but cannot provide input — probing on its own covers spawning, falling, AI and timers only.
- **`inject_input` — scripted keyboard and gamepad input in Play Mode.** Queues device state events through the new Input System (the route with the highest fidelity, because it exercises the game's real bindings), with gamepad buttons and the left stick via `GamepadState`, and a separate `click_ui` action that executes the pointer-click handler on a Button. No arbitrary reflection invocation, no OS-level synthetic input, and the old `UnityEngine.Input` cannot be faked from editor code — a project on the legacy input system only gets a plain error suggesting opt-in hooks. The traps are handled in the handler, not left to the caller: the run saves the focus settings in SessionState, sets them so input gets through while the editor is in the background, and restores them when the run finishes, is cancelled, or a script reload kills it; a tap holds for 3 frames (a press and release inside one input update collapse into nothing); every key and button is released when the run finishes, is cancelled, or Play Mode ends; input goes into the existing keyboard device (never assumed) and the existing gamepad, or one added for the run. The run starts with a self-check — one frame of a key, then confirm the device reports it pressed — and if it never lands, the run fails plainly as "input is being dropped (focus or device disabled)" instead of pretending the game ignored the key. The result also reports whether the app was focused and the device enabled, so a deaf game does not look like a bug in the model's code. Per-frame granularity comes from its own `EditorApplication.update` subscription — the transport polls at 150ms–1s, far too coarse for input; the transport only collects the final result. At most 50 steps, 30 seconds total.
- **App-side `wait` tool and the stop-Play-Mode rule.** A ```wait block with JSON `{"seconds": 5}` (at most 30 — a bare number works too) is just an async sleep in the agent loop, no bridge involved; it sleeps in 250ms chunks so the Stop button ends it. It is the piece that makes state probing possible: enter Play Mode without a duration, wait, read values, stop. The prompt now teaches the two patterns (console-based test vs state probing), the timed run as the recommended default, and the rule: stop Play Mode before finishing unless you asked to leave it running, and never edit code while the game is running.
- **Shared `ComponentLocator` and a JSON writer in the bridge.** Path/component resolution (`FindGameObjects` + `TryResolve` + `GetPath`, including the DontDestroyOnLoad probe) lives in one helper that `read_component_values` uses now and the write actions (next build) reuse; `ReadProperty` is internal static for the same reason (before/after values). The bridge also gains a small hand-rolled `JsonWrite` so handlers can build their `data` as plain values instead of string-building JSON, and the heartbeat now carries `isPlayingOrWillChangePlaymode` and `isPaused` (the app's `parseHeartbeat` / `readHeartbeat` pass them through). `set_play_mode` and the compile action are finalized by one shared `TryFinalizePending` helper in the transport, next to the input finalizer.
- **Version.** package.json is now 0.15.0; the sidebar footer reads "CodeFox 0.15.0 — Local · No account needed". The bridge is now 0.13.0. First compile of the new bridge happens in Rob's Unity, as always — the bridge cannot be compiled on this machine. What can only be proven there: the first compile, the play-mode event ordering on Unity 6.3, input focus behaviour (the focus-settings save/restore and the self-check), and the timed-run round-trip.

## 0.14.0 — 2026-11-26

- **Bridge protocol hardened — the command file is gone.** The bridge no longer talks through `Assets/.codefox-command.json` / `Assets/.codefox-result.json` (a single file the app overwrote directly — a torn read or a second command mid-flight could corrupt it). The protocol now lives in `<project>/.bridge/`, which Unity never imports: `inbox/` (one `<id>.json` per request, written via `.tmp` then renamed so the bridge never sees a half-written command), `processing/` (Unity moves the request here before running it — a file left here after a reload is proof the command was interrupted), `outbox/` (a `pending` result first, then the final result), and `heartbeat.json` (written every poll). Every message carries `protocol: 1`, and the bridge is split into Transport / Dispatcher / Handlers inside the one installed `.cs` file — a dictionary of handlers per action, an unknown action errors with the list of available actions, and a request id on every message. The bridge polls every 1.0s idle and every 0.15s for 5s after any request, skips ticks while Unity is compiling or updating, and deletes outbox files older than 30 minutes. On the app side the runner (`unity-command.js`) reads the heartbeat before sending (older than ~5s and not compiling means Unity isn't responding), waits for the outbox (a `pending` result keeps the command alive with a 60s+ timeout; a compiling heartbeat extends the wait instead of timing out), and deletes the outbox file after reading. `.bridge/` is added to the project's `.gitignore` on install, and the legacy protocol files are removed when the bridge updates. The app never sends an inbox command to an old bridge: `unity:command` updates the bridge first (and waits longer for the first heartbeat after a domain reload). The transport machinery is in the bridge's own `BridgeTransport` / `BridgeDispatcher` / `BridgeResult` types, and the app's `runUnityCommand` is written against an injected filesystem so the whole contract is smoke-tested without Unity.
- **Unity's own compiler — `recompile_and_report_errors`.** The per-edit compile check no longer runs `dotnet build` when Unity is open: the bridge asks Unity itself to compile and reports the errors with file:line, so the check is authoritative and works in a project with no `.sln` at all. The handler keeps its state in SessionState (a successful compile ends in a domain reload, but a compile *with errors* does not — the old assemblies stay and the script stays alive, so a design that only finalizes after a reload would hang forever on exactly the case that matters; a normal poll tick finalizes the request whichever path happened). Caps are 20 errors × 300 characters, 4 seconds for "nothing to compile", 5 minutes hard timeout; a second concurrent compile report is refused. Compile errors come back as `success: false` — the tool worked and the errors are the data, not a bridge failure — and the result is `{"success", "compiled", "errors": [{"file", "line", "message"}], "errorCount", "warningCount"}` with warnings counted only. The app's `runCompileCheck` tries the bridge first (only when the heartbeat is fresh, so a closed Unity costs one fast read, not a 60-second wait) and falls back to the dotnet build check when there is no bridge or no Unity open — dotnet also stays the fallback for the post-turn verify when the bridge can't answer. The agent loop still does one fix round, then restore — it does not adopt 3–5 attempts. One refinement is new: when the first error is identical on two consecutive checks, the model is told to stop and tell the user, instead of trying the same fix again.
- **Unified `readConsole` — the bridge keeps its own log buffer.** The old per-call console read is replaced by a buffer the bridge owns: it subscribes to Unity's public `logMessageReceivedThreaded` and is seeded from the existing console at load (the seed runs once; if a future Unity version ever breaks it, the buffer simply starts empty and everything still works). Entries carry a sequence number, so reads are by cursor — `{"action": "readConsole", "sinceSeq": 0}` for everything since a point, `{"action": "readConsole", "mark": true}` to return just the cursor — earliest first, so the root cause survives truncation. Filters: `minLevel` (0 everything, 1 warnings and errors, 2 errors only), `contains`, `playModeOnly`, `maxEntries` (default 30, hard max 100); the old `"logType": "Error"` / `"Warning"` still works and maps to minLevel 2 / 1. The result carries the next cursor plus `errorCount` / `warningCount` for the window, `omitted`, `hiddenByFilter`, and `missedEvictedEntries` so the model knows what it did not see; consecutive duplicates collapse into one entry with a count (a log in `Update()` is 60 identical lines a second), stacks come back for error entries only, and the buffer keeps 2000 entries with the most recent 500 persisted across domain reloads. The play-test workflow the prompt teaches: mark → run the game → read since the cursor (minLevel 1, playModeOnly) → errors? fix → recompile → repeat. Compile errors stay separate: they go through `recompile_and_report_errors`, runtime errors through `readConsole` — the console is never trusted for compile errors. Log triage now reads earliest-first and treats `omitted` / `missedEvictedEntries` as the lower-bound signal (instead of the old `truncated` flag).
- **Version.** package.json is now 0.14.0; the sidebar footer reads "CodeFox 0.14.0 — Local · No account needed". The bridge is now 0.12.0. First compile of the new bridge happens in Rob's Unity, as always — the bridge cannot be compiled on this machine.

## 0.13.0 — 2026-11-26

- **Skills — progressive loading, per-project enable/disable, manual override.** A skill is a folder of markdown files (a `SKILL.md` plus reference files) that the model reads on demand. Only each enabled skill's name and one-line "use when..." description sit in the system prompt; the full `SKILL.md` is read with the file tools when a task matches, and referenced files after that — so a skill costs almost nothing until it is actually needed, which matters most on a local model's small context window. Skills are opt-in per project, like plugins: built-in skills ship in the repo under `skills/<name>/`, your own skill folders go in the app-data `skills` folder, and a skill only acts in a project once it is installed there (copied to `<project>/.codefox/skills/<name>/`, where you can read it) AND enabled for that project in Settings → Skills. Disabling never deletes files; reinstalling updates a project copy when the shipped version changed. The Settings screen shows a rough token cost of the enabled descriptions and warns when more than 5 are enabled, because routing gets worse with more candidates. `/skill <name>` in chat forces a named skill to load for that turn even when the model's routing misses it (a bare `/skill` lists what is available; a builtin/user skill is installed into the project first — typing the command is the opt-in). The precedence rule is stated in the prompt itself: Project Rules are universal conventions and always win — if a skill conflicts with a rule, the rule wins and the model says so; a skill never silently overrides a rule. The mechanism is the new plain-Node `skill-files.js` (frontmatter parsing, discovery across the builtin/user/project roots, token estimate, `/skill` parsing, prompt-section builder) with new `skillFiles:scan/install/setEnabled` IPCs and a `project_skills` table; the Home screen's Discover Skills (one-click workflow prompts) are a different, older mechanism and are untouched. The bridge is unchanged (still 0.11.0).
- **First built-in skill: unity-multiplayer-networking.** Written from scratch for CodeFox from public Unity documentation — no other tool's skill text, in wording, structure, or examples. It detects which networking stack is installed (packages, manifest, existing assets and config) and tells the user what it found, then stops and asks whether to build on it — never silently adopting or guessing a stack. If none is installed, it asks the user's goals (player count, authority model, hosting, platforms, budget, realtime vs turn-based), suggests 2–4 candidates with concrete trade-offs, lets the user pick, then stops; installing is a manual user step, never programmatic. It reads the stack's setup and examples as ground truth before writing any networked code (networking APIs change between versions; the model must not write them from memory alone) and verifies against the official docs for the installed version. It verifies project configuration before AND after writing code — physics simulation mode and auto-sync transforms, fixed timestep, Input System backend, render pipeline, layers and the collision matrix, transport settings — because code that assumes defaults the project does not have fails silently. Debugging is docs-first: read the debugging references, re-check setup and examples, and run the project-configuration check as the FIRST hypothesis for networking-shaped symptoms ("bullets pass through", "trigger never fires", "works on host not client") — these are usually physics or config bugs wearing a networking costume. It makes the result testable in the Editor (HUD, Multiplayer Play Mode, ParrelSync, a second instance), marks project-changing actions as approval-required, recompiles and reads the console after edits, and never creates documentation unasked. Per-stack references cover Netcode for GameObjects (fullest, first-party default), Photon PUN and Fusion (PUN is in maintenance; Fusion is the successor), FishNet, Nakama, and Metaplay (whose examples are explicitly schematic patterns — the SDK's exact type names vary by version and must be checked against the official docs). The skill's description carries strong "use when..." wording, since the model routes on it.

## 0.12.0 — 2026-11-26

- **Log triage as an automatic pipeline stage — read-only root-cause diagnosis.** When you paste a log (Editor.log, Player.log, a build log, a crash log) or ask why the editor is showing many errors, the turn now routes into triage mode automatically — no subagent, no button, no setting; it is a core flow, on by default. Triage is strictly read-only: it never fixes anything, never modifies a file, scene, prefab, asset or setting, never enters play mode, never reimports, and never triggers a recompile while reading (readConsole already guarantees this), so the evidence is never cleared. It finds the first error that causes the rest, groups repeated entries and counts them, separates your code's stack frames from engine/package/third-party frames and only maps yours to source (viewing the exact lines first), reads source for the root cause plus 2–3 confirming issues, and never guesses from address-only native stacks. Attached logs are read in ranges (start, then end, then narrow toward the first error — never top to bottom); the Unity console is read Error first, then Warning separately, never "All", and a truncated result means the counts are lower bounds. The report is short: root cause in 1–2 sentences, at most 5 quoted log lines with line numbers/timestamps, the file:line, confidence plus what is missing to raise it, other issues grouped with counts, one line of ignored noise, and the suggested fix described — not applied; the fix itself is a later turn. When the cause cannot be established, the report ends with a structured "Request for more information" block (file name, its Windows and macOS paths, why it is needed, findings so far) asking for every file it suspects it will need in one go. Routing is prompt plus a small pure detector (`isLogTriageRequest`, in the new plain-Node `log-triage.js`, mirrored in the renderer like the other pure helpers): a named log file, a many-errors ask, or four or more error lines in a pasted log routes the turn; a single error stays a normal fix turn. Triage turns switch Ask/Plan to Agent mode for the turn (triage needs the file and console tools) and the loop's enforcement can never push a triage turn into outputting a file change — a text-only reply in a triage turn is the report, not a description to enforce — and a refusal in a triage turn is corrected back to diagnosis, never to file output. There is no file-attach UI in CodeFox, so "attaching" a log means pasting it into chat; the log paths the model knows are Editor.log (`%LOCALAPPDATA%\Unity\Editor\` on Windows, `~/Library/Logs/Unity/` on macOS), Player.log (`%USERPROFILE%\AppData\LocalLow\<Company>\<Product>\`, `~/Library/Logs/<Company>/<Product>/`), project logs in `<Project>/Logs/`, and Editor-prev.log after a crash. The bridge is unchanged (still 0.11.0).
- **Version.** package.json is now 0.12.0; the sidebar footer reads "CodeFox 0.12.0 — Local · No account needed". The bridge is unchanged (still 0.11.0).

## 0.11.0 — 2026-11-26

- **The foundation loop — read, edit, compile, console.** The model no longer rewrites whole files blind and only learns about compile errors after a turn. It now reads before it edits, with a ```file block (Agent mode only): `view` reads a file in line ranges with line numbers (at most 200 lines / 32KB at once, truncated with a note); `grep` searches plain text across the project (substring, case-insensitive, not a regex — at most 50 matches, Library/.git/node_modules and the other generated folders never searched, no match is a plain empty result); `str_replace` replaces ONE exact chunk (0 matches or 2+ matches fail plainly — "not found, view the file and check the exact text" / "matched N times, include more surrounding context" — and Windows CRLF files are handled, so the model writing LF still matches). Paths are project-relative and must stay inside the project folder. Reads run immediately with no approval; a str_replace goes through the same write path as any other code file — snapshot first, the approval bar (or auto-accept), the revert bar, and the git-backup hook all treat it as a file change. The prompt teaches "read before you edit — view the exact lines, then str_replace that chunk; never rewrite a whole file to change a few lines." After a round that changed a `.cs` file (whole-file write or str_replace), the loop runs one `dotnet build` check via the existing `unity:buildCheck` IPC and the result comes back as a tool result before the next model turn — "compile clean" means carry on, a failure lists the error tail to fix; a project with no .NET solution reports "no check available", never a failure. Prefab and asset changes are not compiled — the bridge already reports those. And the bridge can now read the Unity console: `readConsole` returns the newest 50 Error (or Warning) entries, each with its message, file:line where Unity knows it, and up to 2 stack lines, plus a `truncated` flag when the console held more — ask for Error first, then Warning separately, never "All". `UnityEditor.LogEntries` has no public API, so the bridge reaches it by reflection (the same pattern shipping tools use, verified against a real implementation) — and reading never calls Clear, Refresh, or anything that recompiles or reimports, so it never clears the evidence it reads. The Diagnose error button is deliberately not wired to readConsole: it would wait up to 60 seconds when Unity is closed — the model already has readConsole as a tool instead.

One check + one fix round, never a retry loop. ## 0.9.0 — 2026-11-26

- **Unity builds prefabs through the bridge — the model never hand-writes `.prefab` / `.unity` YAML again.** Rob asked CodeFox to make a prefab with an Image component, and the model hand-wrote the YAML and invented everything: a made-up script guid, a YAML node literally named `Image:` (Unity: "Unknown type 'Image'"), Button fields on an Image, and no CanvasRenderer. The fix is not a template library or a RAG over Unity docs — it is to stop writing Unity's files by hand and let Unity write them. The bridge (now 0.9.0) gains four actions, and the file writer refuses `.prefab` and `.unity` writes outright. `createPrefab` builds a GameObject tree with Unity's own `AddComponent`: each component type is resolved by reflection over the loaded assemblies (UnityEngine, UnityEngine.UI, TMPro, every UnityEngine.* module, and the project's own Assembly-CSharp scripts), properties are set from JSON (strings, numbers, bools, `[x,y(,z)]` vectors, `[r,g,b(,a)]` or `"#rrggbb"` colours, enum names, asset paths for Sprite / Material / Texture2D / Font / AudioClip — a missing asset fails the whole command plainly, never a null reference), a CanvasRenderer is added automatically when a Graphic needs one, and the file is saved with `PrefabUtility.SaveAsPrefabAsset` (default `Assets/Prefabs/<name>.prefab`). `modifyPrefab` adds, removes, or sets properties on a prefab that already exists (`"object"` is a `/`-separated child path, `""` is the root), loading it with `PrefabUtility.LoadPrefabContents` and unloading without saving when an edit fails, so a failed edit never leaves the file half-changed. `listComponentTypes` lists every non-abstract Component subclass in this install (up to 500, with the total), optionally filtered by substring; `describeComponent` lists a type's settable properties and public fields, walking the inheritance chain so Image shows Graphic's properties too. An unknown type, an unknown property, or a missing asset is a plain failure naming it, with a hint to ask the catalogue — never a guess.
